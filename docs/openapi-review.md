# Сверка с OpenAPI тестового Keitaro

Источник: `openapi.yaml` в корне проекта, предоставлен пользователем 21 ноября 2026 года.

Подтверждено схемой и автоматическими проверками:

- базовый путь `/admin_api/v1`;
- авторизация `Api-Key` в заголовке;
- используемые методы чтения справочников, кампаний и потоков;
- создание кампании: строковый `group_id`, целочисленные `domain_id` и `traffic_source_id`, ротация `position`;
- создание потоков: обязательные `campaign_id`, `schema`, `type`, `name`, `action_type`;
- фильтр страны: `mode=accept`, массив строк в `payload`;
- изменение офферов: `offer_id` и `share` — целые числа, состояния `active`/`disabled`.

## Пробел в документации

`components.schemas.Stream` описывает `action_payload` в ответе, но `StreamObject`, используемый в POST/PUT, этого поля не содержит. Схема при этом не запрещает дополнительные свойства. Приложение передаёт `action_payload` с URL Google и проверяет его после сохранения. Работу этой записи нельзя подтвердить только OpenAPI; требуется успешный ответ реального трекера. Перенос URL в `action_options` без доказательства не выполнен: схема задаёт для этого поля лишь `object`, без структуры.

В экспортированном YAML также есть недопустимые управляющие символы в описаниях из-за повреждённой кодировки. Тестовый загрузчик удаляет только такие символы перед разбором, исходный файл не изменён.

## Проверки

`tests/test_openapi_contract.py` проверяет фактический запрос создания кампании, сформированные потоки, обновление офферов, маршруты и HTTP-заголовок транспорта. Проверка реализует только используемое подмножество схем: `$ref`, `allOf`, свойства, обязательные поля, enum, массивы и скалярные типы. Это не полная валидация OpenAPI. Для `action_payload` есть явное исключение с фиксированным URL Google, отражающее пробел документации.

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
```

## Проверка реального API, 21 ноября 2026

Причина отказа локализована контролируемым сравнением: обычный curl получает 200, тот же curl со стандартным `User-Agent: Python-urllib/3.9` получает 403. Клиент теперь честно идентифицирует приложение заголовком `User-Agent: Adrobot/0.1`.

После изменения Python успешно прочитал кампании (390), домены (1), офферы (1), группы кампаний (38) и источники (1). Настройки Cloudflare не менялись. Это подтверждает доступ и ключ для этих запросов чтения; запись кампаний и фактические географические переходы этой проверкой не подтверждены.

При повторной приёмке исправленная пагинация включила первую активную кампанию. В отдельной отключённой кампании `POST /streams` сохранил URL из `action_payload`, что подтверждено чтением потока. Временная кампания перемещена в архив. `POST /offers` вернул HTTP 403, поэтому для проверки маршрутов и публикации нескольких долей понадобятся тестовые офферы, доступные этому ключу.

Отдельная проверка `POST /streams` для схемы `landings` и типа `default` вернула HTTP 422 при пустом `action_type`. При `action_type: "http"` Keitaro сохранил поток по умолчанию на позиции 2. Обе пробы выполнены на отдельных отключённых кампаниях без привязки офферов. Кампании перемещены в архив.

На проверенном стенде `POST /campaigns/{id}/enable` и `POST /campaigns/{id}/disable` возвращают HTTP 200 с массивом из одного объекта кампании. OpenAPI описывает одиночный объект. Adrobot принимает обе формы для этих двух методов, сверяет ID и перечитывает состояние кампании после записи. Перед подтверждением создания он также перечитывает оба потока.
